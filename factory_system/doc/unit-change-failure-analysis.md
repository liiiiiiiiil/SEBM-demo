# 单位变更失败场景分析与解决办法

## 一、概述

本文档分析在**原料（Material）和成品（Product）单位变更**过程中，可能导致失败的各种情况，并给出可行的解决办法。**不涉及代码修改**，仅作分析与建议。

---

## 二、失败场景分类

### 2.1 输入校验失败

| 场景 | 触发条件 | 当前表现 | 失败原因 |
|------|----------|----------|----------|
| 新单位为空 | 用户未填写或提交空字符串 | 视图层校验，redirect 并提示“请输入新单位” | 必填项校验 |
| 转换系数为空 | 用户未填写转换系数 | 同上，“请输入转换系数” | 必填项校验 |
| 转换系数格式错误 | 输入非数字（如字母、符号） | `Decimal(conversion_factor_str)` 抛出 `InvalidOperation`，捕获后提示“转换系数格式错误” | 类型转换异常 |
| 转换系数≤0 | 输入 0 或负数 | 校验后 `ValueError`，提示“转换系数格式错误” | 业务规则（不能除零或反向换算） |
| 变更原因为空 | 用户未填写原因 | 提示“请输入变更原因” | 审计要求 |

**解决办法：**

- 前端：对“新单位、转换系数、变更原因”做必填和格式校验，减少无效提交。
- 产品：在界面明确说明转换系数含义（如“1 新单位 = 转换系数 × 旧单位”）并给出示例。
- 流程：若需审批，可在审批环节再次校验上述项。

---

### 2.2 前置检查（业务冲突）导致“不可变更”

当前逻辑中，`check_can_change_unit` 仅当存在 **errors** 时才会将 `can_change` 置为 `False`；**warnings** 不会直接阻止变更，但会提示用户。

| 检查项 | 类型 | 说明 | 若未来改为“有 warning 即禁止”时的失败原因 |
|--------|------|------|--------------------------------------------|
| 进行中的生产任务 | warning | 存在使用该物料的领料单且任务状态为 pending/approved/in_progress | 生产任务仍按旧单位领料，变更后数据口径不一致 |
| 未完成的采购任务 | warning | 存在包含该物料的待审批/已审批/采购中任务 | 采购单按旧单位，与主数据不一致 |
| 未完成的销售订单 | warning | 通过 BOM 关联到使用该物料的成品，且订单未完成 | 订单、生产、库存单位口径不一致 |

**当前行为：**  
若业务上配置为“仅 errors 阻止变更”，则上述情况不会导致**失败**，只会提示警告；用户仍可勾选“强制变更”继续。

**若希望“有业务冲突即禁止变更”时可能失败的情况：**

- 存在上述任一类未完成任务/订单，且策略为“禁止变更”时，应返回明确错误（如“存在进行中的生产任务，不允许变更单位”），并**不**执行变更。

**解决办法：**

- **策略一（当前思路）：** 保持“warnings 不阻止 + 强制变更”。在界面上清晰列出冲突（生产/采购/销售单号、数量等），并说明“强制变更后，这些单据仍按旧单位显示，新业务按新单位”。
- **策略二：** 若业务要求“有冲突一律禁止”，则在 `check_can_change_unit` 中把相应 warning 提升为 error，或增加配置项“是否允许在存在冲突时强制变更”。
- **策略三：** 提供“冲突清单”和操作建议：如“请先完成或取消以下生产任务/采购任务/销售订单后再变更”。

### 2.3 数据转换与计算异常

| 场景 | 触发条件 | 可能异常 | 失败原因 |
|------|----------|----------|----------|
| 转换系数为 0 | 虽前端/视图已校验，但若接口被直接调用传入 0 | `old_unit_price / Decimal('0')` → 除零 | 数学上无效 |
| 转换后数值溢出 | 数量或单价 ×/÷ 系数后超出模型 `max_digits`/`decimal_places` | `Decimal` 结果超出 `DecimalField` 范围，`save()` 时数据库或 Django 校验失败 | 字段精度限制 |
| 转换后精度过长 | 例如 `1/3` 导致无限小数 | 若未做 `quantize`，可能和数据库精度不一致或触发数据库错误 | 精度与模型定义不一致 |
| 极端大/小系数 | 极大系数导致数量爆炸，极小系数导致单价爆炸 | 同上，溢出或不符合业务 | 输入不合理 |

**解决办法：**

- 在服务层执行换算**前**再次校验：`conversion_factor > 0`，避免除零。
- 对换算结果做 `quantize` 到与模型一致的小数位（如 2 位），再写库。
- 根据模型定义（如 `max_digits=10, decimal_places=2`）在换算后做范围检查，超出则拒绝并提示“转换后数值超出系统范围，请调整转换系数”。
- 对转换系数设置合理上下限（如 0.0001～10000），并在界面说明，避免极端值导致溢出。

### 2.4 数据库与并发异常

| 场景 | 触发条件 | 可能异常 | 失败原因 |
|------|----------|----------|----------|
| 唯一/外键约束 | 历史表、关联表在 save 时违反约束 | `IntegrityError` | 数据不一致或并发导致违反约束 |
| 事务中断 | 在 `@transaction.atomic` 内任一步（物料/库存/批次/历史）失败 | 整个事务回滚，变更未生效 | 某条 save 或 create 失败 |
| 并发修改同一物料 | 两个用户同时对该物料执行单位变更 | 后提交的可能覆盖先提交的，或触发锁等待/死锁 | 缺少乐观锁或悲观锁 |
| 数据库连接断开 | 执行过程中连接超时或断开 | 连接类异常，事务回滚 | 网络或数据库问题 |
| 记录不存在 | 变更过程中物料被删除（如另一请求） | `Material.DoesNotExist` 或关联查询失败 | 并发删除与变更 |

**解决办法：**

- 保持当前“单位变更”在**单事务**内完成（物料 + 库存 + 批次 + 历史），确保要么全成功要么全回滚。
- 对“单位变更”这类敏感操作，考虑对**当前物料行**加悲观锁（`select_for_update()`），避免并发变更同一条物料。
- 若使用乐观锁：为 Material 增加 `version` 或 `updated_at`，保存前校验是否被他人修改，若已修改则提示“数据已被修改，请刷新后重试”。
- 对关键操作记录详细日志（物料 ID、操作人、转换系数、异常栈），便于排查 IntegrityError、死锁等。
- 数据库侧：合理设置锁等待超时与连接池，避免长时间占用连接。

### 2.5 关联数据缺失或状态异常

| 场景 | 触发条件 | 可能异常 | 失败原因 |
|------|----------|----------|----------|
| 物料/成品不存在 | 提交时 material_id/product_id 已删除或错误 | `get_object_or_404` 返回 404 | 数据已删或 URL/参数错误 |
| 库存不存在 | 物料有库存业务但尚未建 Inventory 记录 | 当前实现：`Inventory.DoesNotExist` 已处理，inventory=None，不会抛错 | 若未来逻辑假设 inventory 一定存在则会失败 |
| 变更人不存在 | changed_by 对应用户已被删或未传 | `User` 外键 PROTECT，若用户被删则无法删除依赖；创建历史时若用户无效会失败 | 权限或数据一致性问题 |
| 审批人未传 | 非自动审批时 approved_by 为 None | 若模型未设置 null=True，create 时报错 | 模型约束与业务未对齐 |

**解决办法：**

- 执行变更前再次用当前请求的物料/成品 ID 查询一次，若不存在则直接返回“物料不存在”或 404，避免在事务中途才发现。
- 明确“无 Inventory 时是否允许变更”：若允许，保持“无则只更新主数据、不更新库存/批次”；若不允许，在检查阶段就提示“请先初始化库存再变更单位”。
- 变更人与审批人：仅允许选择当前有效用户，或在使用前校验用户是否存在且未禁用。
- 对 Product 的成品单位变更，若存在 SalePrice、Inventory、Batch 等，需同样检查关联是否存在、是否允许为空，避免因关联缺失导致 save 失败。

---

### 2.6 权限与登录

| 场景 | 触发条件 | 表现 | 失败原因 |
|------|----------|------|----------|
| 未登录 | 未登录用户访问单位变更页面或接口 | `@login_required` 跳转登录页 | 鉴权 |
| 无权限 | 用户无 warehouse/ceo 等所需角色 | `@role_required` 返回 403 或错误页 | 权限控制 |

**解决办法：**

- 前端：根据用户角色隐藏或禁用“单位变更”入口，减少 403 请求。
- 产品：在说明中写清“仅仓库管理员/总经理可执行单位变更”。
- 审计：所有单位变更均记录 changed_by，便于追溯。

---

### 2.7 成品（Product）单位变更特有风险

若已实现或计划实现成品单位变更，除与原料类似的前置检查、换算、事务、并发外，还有：

| 场景 | 说明 | 失败原因 |
|------|------|----------|
| 未完成销售订单 | 订单行已按“件”下单，若成品改为“箱”且不转换订单，则口径混乱 | 若策略为“有未完成订单则禁止变更”，则此时会失败 |
| 售价字段 | Product 有 sale_price，需按同一系数换算；若漏算或算错则前后不一致 | 数据不一致或校验失败 |
| 生产任务 | 进行中的生产任务需求数量、完成数量均为旧单位 | 同原料，若禁止“有进行中任务时变更”则会失败 |
| BOM 配方 | 成品单位变更不直接改 BOM，但 BOM 用量单位若与成品单位强关联，可能需人工检查 | 未自动同步导致后续生产计算错误 |

**解决办法：**

- 成品单位变更前检查：未完成销售订单、进行中生产任务、BOM 使用情况；与原料类似，可采用“禁止 / 警告+强制 / 仅提示”三种策略之一。
- 售价与单价统一按“新单价 = 旧单价 ÷ 转换系数”等规则换算，并在变更历史中记录 old_sale_price/new_sale_price。
- 成品变更后，在界面或报表中提示“请检查使用该成品的 BOM 及销售订单单位是否需人工调整”。

## 三、按阶段的失败点汇总

| 阶段 | 可能失败点 | 建议措施 |
|------|------------|----------|
| 提交前（前端/视图） | 新单位、转换系数、原因为空或格式错误 | 前端校验 + 视图层再次校验并友好提示 |
| 前置检查 | 业务冲突（生产/采购/销售）若配置为禁止则不可变更 | 明确禁止/警告+强制策略，并展示冲突明细与操作建议 |
| 换算过程 | 除零、溢出、精度问题 | 系数二次校验、结果 quantize、范围检查、系数上下限 |
| 持久化 | 约束冲突、事务内某步失败、并发覆盖 | 单事务、行级锁或乐观锁、日志与监控 |
| 关联与权限 | 物料/用户不存在、无权限 | 存在性校验、权限控制、审计记录 |

## 四、建议的预防与兜底措施（不修改代码的维度）

1. **操作规范**
   - 在操作说明中明确：何时允许/禁止单位变更、转换系数含义、强制变更的影响。
   - 建议在业务低峰期执行单位变更，减少并发与业务冲突。

2. **数据与备份**
   - 重要单位变更前对相关表（物料/成品、库存、批次、历史）做备份或快照，便于回滚或对比。

3. **监控与审计**
   - 记录每次变更的物料/成品、操作人、转换系数、变更前后快照；对失败请求记录原因（校验失败、业务冲突、异常信息）。
   - 对“强制变更”单独标记，便于后续核对未完成单据与主数据差异。

4. **业务策略**
   - 明确：仅 warning 时是否允许强制变更、是否将某类 warning 升级为 error。
   - 成品单位变更是否与销售订单、生产任务、BOM 联动（仅提示 vs 禁止变更）。

5. **异常与回滚**
   - 若事务回滚，界面上应提示“变更未生效，请检查输入或联系管理员”，避免用户误以为已变更成功。
   - 若有变更历史表，可考虑支持基于历史记录的“按记录回滚”功能（需单独设计与实现）。

---

## 五、总结

- **会直接导致“修改单位失败”的情况包括：**  
  输入校验不通过、前置检查被配置为禁止且存在业务冲突、换算过程除零/溢出/精度错误、数据库约束或事务内任一步失败、并发冲突、关联数据缺失、权限不足等。
- **不修改代码可做的：**  
  规范操作流程、明确业务策略（禁止/警告+强制）、做好备份与审计、在界面与文档中说明转换系数与风险、建议低峰期操作、对异常与回滚做清晰提示。  
- **若后续要改代码：**  
  ​可重点在服务层增加：转换系数二次校验、结果 quantize 与范围检查、select_for_update 或乐观锁、更细粒度的错误码与提示信息，以及成品单位变更时对 sale_price 与业务冲突的完整处理。
